# Coding standards

Rules a reviewer checks a diff against. Each has an id to cite and the reason it exists. `pnpm typecheck`, `pnpm lint` and `pnpm test` enforce part of this; the rules below are the part a reviewer has to look for, plus the ways the automated checks can be sidestepped.

## Database boundary

- **DB-1** Only files under `packages/core` import a SQLite driver (`better-sqlite3`, `node:sqlite`, or any other listed in `biome.json`). *Why: the invariants below live in core's functions and schema. A second connection skips the functions.*
- **DB-2** `better-sqlite3` is a dependency of `packages/core/package.json` and of no other package. *Why: pnpm then refuses to resolve it elsewhere, a second lock behind the lint rule.*
- **DB-3** Other packages import core as `@x-bookmarks/core`, never by another subpath or a relative path. The one subpath is `@x-bookmarks/core/testing`, which test files import for the temporary-database helpers of TEST-1 and for `readFixture`. *Why: its internal modules hold the connection. The helpers import Vitest, so they cannot be part of the main entry.* The end-to-end test runs under `node --test` and cannot load that entry, so it reads the one fixture it serves as a file, by path.
- **DB-4** Nothing exported from `packages/core/src/index.ts` returns a connection or statement, or accepts SQL text. `connectionOf` is not exported there. *Why: either would reopen DB-1 through the front door.*
- **DB-5** Outside core, nothing loads a module by name at run time. Lint enforces the nameable forms in every file type, `.cjs`, `.cts` and `.mjs` included: `lint/sqlite-boundary.grit` fails any mention of `require`, `createRequire` or `getBuiltinModule`, and `noRestrictedImports` fails importing `createRequire` under another name. What is left for a reviewer: no `biome-ignore` on any of these checks, no override that relaxes them or drops the plugin beyond the existing `packages/core/**` ones, no `import()` whose argument is built at run time, and no computed access such as `process["getBuiltinModule"]`. *Why: these are the routes to a SQLite driver that the import restriction of DB-1 does not read. A `.cjs` file used to pass lint with `require("better-sqlite3")` in it.*
- **DB-6** In `packages/web`, core's functions are imported from `src/server/core.ts`, and only types from `@x-bookmarks/core` directly. Test files are exempt. *Why: Next bundles a workspace package once per server layer, so a direct import gives the process several copies of core, and a store opened by one copy is rejected by the others. `core.ts` has Node load the single real one.*

## Raw captures

- **RAW-1** The `payload` given to `insertRawCapture` or `insertRawCaptureOnce` is the response text as received: not parsed and re-serialised, trimmed, or filtered. The same holds for `requestBody`. *Why: re-serialising rounds integers above 2^53, and anything dropped is gone when a parser later needs it.*
- **RAW-2** A response is stored with `insertRawCapture` before anything is parsed from it, including responses no parser handles yet. *Why: X changes its response shapes a few times a year and the breakage is silent; stored captures are how the gap is recovered.*
- **RAW-3** No code or migration updates or deletes `raw_captures` rows, and the `raw_captures_no_update` and `raw_captures_no_delete` triggers stay. *Why: every parsed row must be reproducible from its capture.*
- **RAW-4** `source` is a member of `CAPTURE_SOURCES`. A new capture route is added to that list in the same diff. *Why: parsers are chosen by `(source, operation)`; a misspelt source is a capture no parser will ever read.*
- **RAW-5** A capture that can be delivered more than once is stored with `insertRawCaptureOnce`, under an id its capturer assigned before the first attempt. *Why: a queue that retries will re-send a capture whose acknowledgement was lost, and a second row would be a second sighting.*

## Parsing

- **PARSE-1** A parser is a pure function from a payload's text to a `ParsedCapture`, in `packages/core/src/parsers/<source>/<operation>.ts`, registered in `parsers/index.ts`. It opens no database and reads no clock. Its one other input is the stored body of the request that produced the response, for a mutation, which names its post only there. *Why: a re-parse must give the same result from the same capture, whenever it runs.*
- **PARSE-2** A parser reads a response through the readers of `parsers/shape.ts` and returns what it does not understand: a payload of an unknown shape as `outcome: "failed"`, an entry as `kind: "failed"`, a part of a post as a warning. It never returns an empty result for a response it did not understand, and never fills a field from a shape it has no case for. *Why: X changes these shapes without notice and the breakage is silent. An empty page and a broken parser must not look alike.*
- **PARSE-3** Every timeline entry that is not a cursor is accounted for: a bookmark, a post X withholds, or a failure. One entry failing does not fail the others. *Why: a new kind of post must cost that post, not the page.*
- **PARSE-4** A `ShapeIssue`, and so every `parse_issues` row, holds a path, field names and type names only: no value from the response, and no message of a thrown error that could quote one. *Why: issues are shown on the status page, printed by `pnpm reparse` and pasted into bug reports. `Bookmarks.test.ts` plants a secret in each kind of mismatch and looks for it.*
- **PARSE-5** Bookmarks are written from a response by `parseCapture` and by nothing else, and `capture_parses`, `parse_issues` and `bookmark_mutations` are written only there. No code edits a bookmark's parsed content in place. *Why: everything parsed must be reproducible by `reparseAllCaptures`; a hand-applied fix is undone by the next re-parse, or worse, is not.*
- **PARSE-6** A change to what any parser returns for the same payload raises `PARSER_VERSION`. *Why: the status page counts captures parsed by another version as waiting for a re-parse; without the bump, stale results look current.*
- **PARSE-7** A response is stored before it is parsed, in a separate step, and the answer to whoever delivered it depends on the storing alone. A failure to parse is caught and recorded, never returned as a failure to ingest. *Why: the extension deletes a capture from its queue only when told it is stored, and re-sends it otherwise. A parser bug must neither lose a capture nor make the extension send it for ever.*
- **PARSE-8** `reparseAllCaptures` run twice in a row changes no row the second time. *Why: it is run to find out whether anything changed. `parsing.test.ts` compares every derived row.*
- **PARSE-9** A parser, and a new shape in an existing one, arrives with a fixture built from a real capture by `pnpm fixtures:build` and a test against it. Nothing is parsed from a shape known only from another project's source or from a guess. *Why: the invented response the capture phase was tested with shares almost no field with the real one. A parser tested against an invented shape shows nothing about X's.*

- **PARSE-10** What is derived from captures is the same whatever order they are parsed in. A capture can reach the library late, after newer ones were parsed, so nothing may depend on arrival order: `upsertBookmark` keeps the content of the most recently received sighting, and `bookmark_mutations` keeps the latest capture of each kind. *Why: the extension queues and retries, and a full re-parse replays oldest first. The two must agree, or a re-parse changes the library. `mutations.test.ts` parses the same captures in several orders.*

## Removed on X

- **REM-1** Whether a bookmark is removed on X is read, never stored: `removedOnXAt` is the time of the latest `DeleteBookmark` X confirmed for the post, when that is later than both the latest `CreateBookmark` and the bookmark's `last_seen_at`. No column holds a removed flag, and no code clears one. *Why: the user decided that a removed bookmark stays, marked with the time, and that bookmarking it again clears the mark. Bookmarking again is seen two ways, as a mutation or as the post back in the timeline; a stored flag would need both writers to remember it.*
- **REM-2** Nothing deletes a bookmark because it was removed on X, and a mutation never creates one. A mutation carries a post id and no content; its row in `bookmark_mutations` waits for a sighting. *Why: X-2. The post's content cannot be asked for.*
- **REM-3** A mutation counts only when X answered `Done`. Any other answer is a capture that failed to parse. *Why: an error from X must not read as a bookmark removed.*
- **REM-4** A query function leaves out removed bookmarks unless its caller passes `includeRemoved`, for those as well, or `onlyRemoved`, for those alone. `summariseMatches` counts them apart, as `removedOnX`, whatever the caller chose. *Why: the default answer to "what have I saved" is what is still saved.*

## Reading the library

- **READ-1** Features read bookmarks through `searchBookmarks`, `listBookmarks`, `getBookmark` and `summariseLibrary`, with `summariseMatches` for the counts beside a screen's filters and `listWithheldPosts` for the posts X no longer sends. Category, format and tags are filters of those functions (`category`, `format`, `tags`, `classified`) and counts of the two summaries, like every other. A new kind of question becomes a new option or function in `packages/core/src/library.ts`, with tests. The library UI's one data module, `packages/web/src/server/library.ts`, turns the screen's query into core's filter and core's answers into the screen's shapes, and holds no query, search or filter of its own. *Why: the MCP server, the UI, tagging and the digest must agree on what "removed", "this week" and "matches" mean.*
- **READ-2** "When was this bookmarked", for ordering and for periods, is `bookmarkedAt`: the later of `observedBookmarkedAt` and `estimatedBookmarkedAt`, or `firstSeenAt` when there is neither. A feature does not pick among the three itself. *Why: this is the decision SEEN-4 left open. The observed time is exact but rare, the estimate covers everything but rests on an undocumented value, and after a backfill first-seen is one day for the whole library. The later of the first two is the bookmark that now stands, when a post was bookmarked twice.*
- **READ-3** A result is bounded: `limit` is at most `MAX_PAGE_SIZE`, and a function that returns bookmarks returns `total` beside them. A screen that keeps a list open and reads it a page at a time for as long as its reader scrolls, as the library UI does, continues from `nextCursor` with `after`; a search is ranked and has only `offset`, so its reader drops an item it is sent twice. *Why: a result goes into a model's context or a page, and an unbounded one grows with the library. An offset moves under a reader when a capture arrives between two pages, and repeats a bookmark.*
- **READ-4** What a user or a model typed never reaches FTS5 as syntax. `parseSearchQuery` quotes every term. *Why: a stray quote or colon would otherwise be a syntax error, and a crafted query could address columns.*
- **READ-5** The search index is derived data. `bookmark_search` equals the view `bookmark_search_text`, kept so by triggers, and the update trigger fires only when something searchable changed. A change to what is indexed is a migration that drops the index, redefines the view and fills it again. A change to how text is folded is made in the view and in `search-text.ts` together. *Why: the index has to be right after an ingest and after a re-parse without either knowing it exists; and an index rewritten by every unchanged upsert makes every snapshot differ.*
- **READ-6** Text is folded and matched in `packages/core/src/search-text.ts` and nowhere else. What a search found is marked for a reader by `markMatches`, given the terms `searchBookmarks` returned; nothing else folds text to compare it with a search or looks for a search's terms in it, the browser included: the library UI marks on the server and sends the marks. *Why: a second folding drifts from the index's, and then a post is listed with nothing marked in it, or marked where it did not match. The UI was first built with one of its own.*
- **READ-7** Whether X withholds a bookmark's post is read, never stored, like a removal (REM-1): `withheldOnXAt` is the time of the latest capture that found the post withheld, when that is later than the bookmark's `last_seen_at`. The bookmark stays in every list; `onlyWithheld` asks for those alone, and a withheld post the library never held is no bookmark and comes from `listWithheldPosts`. *Why: X-2. The copy captured before is all there will ever be, and a later capture that holds the post again must clear the mark without anyone remembering to.*
- **READ-8** A week is a `Week` of `packages/core/src/weeks.ts`: seven local days from a Monday's midnight, in the process's time zone, taken over `bookmarkedAt` (READ-2), and named by the date of its Monday. The week a digest is for when none is named is `latestWeekEnded`: the one that last reached Sunday at `WEEK_ENDS_SUNDAY_AT_HOUR`. No feature works out a week's bounds, its name or "the latest week" itself: the page, the command, the MCP server and the launchd job all go through those functions. A week's counts are `summariseWeek`, and the weeks there are, `listWeeks`; the free part of a digest is read from the bookmarks each time and stored nowhere. `packages/web/src/server/digest.ts` is the digest page's one data module, on the terms of READ-1. *Why: a week that begins on Sunday in one place and Monday in another, or ends at 24 hours times seven where the clocks changed, is two digests that disagree about one bookmark.*

## MCP server

- **MCP-1** `packages/mcp` opens the database with `openStore(path, { readOnly: true })` and imports from core only functions that read. `src/server.test.ts` pins the list; a new entry is its own explained change. *Why: everything the server returns was written by strangers, and a model can be talked into things. That it has nothing to write with is what bounds the damage.*
- **MCP-2** The server makes no network request and loads no module that could: `src/server.test.ts` pins its imports, and X-4 lists its files. Its one transport is the standard input and output it was started with. *Why: it reads the whole library, and must have nowhere to send it.*
- **MCP-3** A tool returns one JSON document that opens with `NOTICE`, and its description ends with the sentence that says the content is other people's text and not instructions. Text from a bookmark goes out through `visible()`. A bookmark's category, format and tags are the library's own words, ids of the taxonomy, and the notice says so; a tag the classifier only proposed is not one of them and is on no bookmark a tool returns. `get_digest` is where the other things a model wrote go out, each marked as that and covered by the notice: the prose of a written digest, through `visible()`, pointing at bookmarks by id alone; and the proposed tags, by name, apart from every bookmark. *Why: a post that contains instructions has to arrive as a quoted string inside clearly marked data, and so does a summary a model made of such posts.*
- **MCP-4** No result holds a URL on X's media or link-shortener hosts, and the instructions tell the client never to request an X host. *Why: X-1 binds the agent that uses the server too, and a model handed an image address may try to open it.*
- **MCP-5** Nothing the server writes to standard error quotes a bookmark or a query. *Why: Claude Desktop keeps that output in a log file.*

## Backups

- **BAK-1** A snapshot is taken by `backupStore` and verified before it gets a snapshot's name: SQLite's integrity check, the same schema, and every raw capture equal to the database's. A file named `snapshot-<time>.db` has passed. *Why: the captures were collected by hand and cannot be collected again; a backup nobody checked is a hope.*
- **BAK-2** `backupStore` deletes only files it named, beyond the newest `keep`. *Why: the directory also holds copies made by hand.*
- **BAK-3** Snapshots go outside the repo: beside it by default, or where `X_BOOKMARKS_BACKUP_DIR` says. A test or a tool that moves the data directory with `X_BOOKMARKS_DATA_DIR` gets its snapshots inside that directory. *Why: PRIV-1 and TEST-4. A test must never write into the user's backups.*
- **BAK-4** The app's own backup never throws and never fails silently: `backUpIfDue` records the failure, and until a backup succeeds every screen shows it: the Backups card on the status page, and the library's status line and banner, as a problem like a capture that was not understood. *Why: a backup that stopped working is only discovered when it is needed, and the status page is a page nobody opens while all seems well.*
- **BAK-5** A library that has not changed is not copied again. *Why: otherwise the newest `keep` snapshots of an idle library are all the same state, and an older, good one is pushed out.*

## Requests to X

The account that made the bookmarks is the asset at risk. Accounts have been suspended over extensions that sent their own requests to X, and none are reported for reading what the page already loaded. So this project takes what X's own page was sent, and asks X for nothing, with the one exception the user decided: media they ask to see, under X-7 to X-11. That holds for every phase, tagging included, which sends a post's stored text to the Claude API and asks X for nothing to add to it (AI-4), and the weekly digest, which sends the same of a week's posts on the same terms (AI-11) and whose page draws posts with the library's own components, under X-7 to X-11; and for an agent at work on the repo as much as for the code it writes.

"A host X owns" is any host `isXOwnedHost` in `packages/core/src/x-hosts.ts` says yes to: `x.com`, `twitter.com`, `t.co`, `twimg.com`, the other domains in `X_OWNED_DOMAINS`, and every subdomain of them. That takes in the API (`api.x.com`), link redirects (`t.co`), the media CDN (`pbs.twimg.com`, `video.twimg.com`), oEmbed (`publish.twitter.com`) and the syndication endpoints (`cdn.syndication.twimg.com`).

- **X-1** No code in this repo, and no agent or person working on it, sends a request to a host X owns: no fetch, download, HEAD, redirect lookup, embed, scrape, headless browser, API call or shell command, logged in or not, whatever it is for. The exceptions are two, and both are the user acting in their own browser: visiting X by hand, and the media of X-7. *Why: X sees the request and whose session or address it came from, and no feature here is worth the account. "Logged out" and "public endpoint" are not exceptions: the syndication and oEmbed endpoints are X's, and a burst of them from the user's address is still automation aimed at X.*
- **X-2** Missing data stays missing. When a capture lacks something (the rest of a thread, an article's body, a media variant, where a `t.co` link leads, a quoted post that came back as a tombstone, a post X now withholds), the parser records it as absent, and nothing resolves, expands or downloads it later. A feature that would need the missing part is built without it, or waits for the user's browser to be sent it and the extension to capture it. *Why: every way of filling a gap is a request to X. The stored `t.co`, `twimg.com` and `x.com` URLs in a bookmark are data to show or search, never addresses to call.*
- **X-3** Code that requests a URL it did not write itself (a link from a post, a card's target, an image) passes it through `assertNotXOwnedUrl` first, requests with redirects switched off, and passes each redirect target through it again. The media of X-7 is the one thing loaded that is X's; it is loaded by the user's browser, never by this rule's kind of code, and its address passes through `xMediaUrl` instead. *Why: a bookmark's links are mostly not X's, and a later phase may have reason to fetch one. The guard is what keeps "fetch this link's title" from fetching a post, and a shortener that redirects to `x.com` is a request to X at one remove.*
- **X-4** `packages/core/src/no-requests-to-x.test.ts` passes, and its three lists are kept honest: a file that names a host X owns is in `NAMES_X_HOSTS` with what the name is for; a file that makes requests, or has a browser load something, is in `MAKES_REQUESTS` with where they go; a file that does both is in `REQUESTS_BESIDE_X_HOSTS` with why they cannot meet. A new entry in any of them is its own explained change, and one in the third list is checked by hand. No entry is added to get a failing test to pass. *Why: a written rule alone depends on someone remembering it. The test turns "this file talks to the network" and "this file knows X's address" into decisions that appear in a diff.*
- **X-5** `packages/core` makes no request of any kind. *Why: it holds every bookmark and every stored URL. The same test checks it.*
- **X-6** The extension's part is CAP-1 to CAP-3: it starts no request, and its service worker holds no host permission for X. The end-to-end test's browser resolves every hostname to a server inside the test and stops before any test if that rule is not in force.

What the test cannot see, and a reviewer therefore has to: a URL that reaches a request as data, which is why X-3 exists; a request made inside a dependency; a host name assembled from parts or decoded at run time; a redirect; and anything done outside the repo, such as a command an agent runs in a shell. It reads source files only. It skips `docs/` and Markdown, which cite X's pages in prose, and the redacted fixtures, which are data.

### Media the user asks to see

Decided by the user on 2026-10-12, when the library UI was built. A bookmark's photos, videos, link-card pictures and article covers are on X's media CDN, so showing one is a request to a host X owns, made by the user's browser. The user's worry was a burst of a thousand such requests from one address, which is what loading a list's media is. The decision puts every request behind the user's own act. A plain link the user chooses to click, to open a post on X, is the user's own navigation and is fine; nothing may load, prefetch or preconnect to X on its own.

- **X-7** The library UI may have the user's browser load a post's media, and only in two cases. One: the user presses "Show media" on a post, which loads that post's media and no other post's; a quoted post is a post of its own, with its own control. Two: the user has turned on "Load media on screen", a setting that is off by default and kept in that browser alone, and a post's media placeholder has been at least half inside the viewport of a visible tab for `AUTO_MEDIA_DWELL_MS`. In both, a video file is requested only when the user presses play. *Why: each request then follows a click, as clicking through to the post would, or is one of a screenful the user is looking at. Scrolling past a post, or jumping over a hundred, asks X for nothing.*
- **X-8** Until a post's media is revealed, the page holds no element for it: no `<img>`, `<video>`, `<source>`, CSS background, `srcset`, `poster`, `loading="lazy"`, preload, prefetch or preconnect that names its address. The media elements are written in `packages/web/src/components/library/x-media-element.tsx` and nowhere else, and rendered by `media.tsx` alone, inside a revealed `MediaScope`. *Why: a browser loads ahead of need wherever it is allowed to. Its preload scanner reads tags before any script runs, native lazy loading starts more than a screen early, and a long list renders rows that are off screen. An element that does not exist cannot be loaded early by any of them.*
- **X-9** Avatars are never loaded, in any mode, and no view sent to the browser carries an avatar's address. The UI shows initials. *Why: they are the most requests per screen for the least value.*
- **X-10** No server code requests, proxies, resizes or stores X media, ever: no `next/image`, no route that takes a media address, no download. The browser's own cache is the only cache. *Why: a request from the server is this app's request, made whenever and for however many, and X-1 stands for it without exception.*
- **X-11** A media request is as plain as an element can make it. Its address has passed `xMediaUrl` in `packages/web/src/lib/x-media-policy.ts`, which admits HTTPS on `pbs.twimg.com` for pictures and on `video.twimg.com` for video, and nothing else. The element carries `crossOrigin="anonymous"`, so the browser sends no cookie and no stored credential, and no `Referer` is sent, by the element's `referrerPolicy` and the page's own. Every page is served with a Content-Security-Policy, built in the same file, whose `img-src` and `media-src` admit this app and those two hosts alone and whose `connect-src` admits this app alone. *Why: the request should say as little about the user as a request can, and the browser should refuse any address the code was not meant to load, whatever a capture's data says.* A request without credentials still carries an `Origin` header naming the app's local address; that is what the browser sends for one, and it is accepted.

Checked by `packages/web/src/lib/x-media-policy.test.ts`, which pins the address check, the policy, which files hold and render the elements, and that nothing touches an avatar's address; and by the media tests at the end of `packages/e2e/src/capture.e2e.ts`, where the media hosts are the fake, hold a cookie, and record what a real browser asked them for: nothing by default, one post's pictures after one press with no cookie and no `Referer`, a video file only on play, and with the setting on the posts on screen and none of those passed over. A video plays in the app's own player, `video-player.tsx`, which is handed the element and drives it: it adds no request, names no address, and tells the element to load again only when the owner presses "Try again". The same tests show that in it play is what asks for the file, a GIF's included, and that nothing else it does asks any host for anything. A change to any of X-7 to X-11 is the user's decision, and is made here first.

The library list draws only the rows near the screen (`library-list.tsx`). A row in which media has been revealed is kept in the page from then on, wherever the list is scrolled to: taken out and drawn again, it would make new elements and ask X's CDN for the same media a second time, unasked. The end-to-end test shows a row's shown media, and a playing video, kept while the list is scrolled to its other end and back, with nothing asked for again by a fake host that allows no caching. Rows drawn ahead of the screen load nothing: the on-screen setting still goes by what is on the screen itself.

The media elements' file and the player's are in `MAKES_REQUESTS`, and the policy's file is in `NAMES_X_HOSTS`, each with its reason, as X-4 asks. What no test here can show, because no test may ask X: that X's CDN answers a request without credentials with the header that lets a page display the result. If it does not, a revealed picture shows "Did not load", and nothing falls back to a request with credentials.

## Labels: category, format and tags

A bookmark is filed under one category, one format and a few tags, by a classifier model, and the owner can correct any of them.

- **LAB-1** The categories, the rules between them and the formats are `TAXONOMY` in `packages/core/src/taxonomy.ts` and are written nowhere else. They are fixed in that file and changed there, deliberately. The classifier's instructions and output schema, the filters' checks, and the MCP server's descriptions and overview are built from it. No other source file spells out a category or a format, tests apart; the two ids code needs by name are the exported `OTHER_CATEGORY` and `UNCLEAR_FORMAT`. *Why: a change to a category must be one edit to one file. A category listed twice is a category that is changed once.*
- **LAB-2** The tag vocabulary is in the database and nowhere else: the tables `tags` and `tag_aliases`, with every change in `vocabulary_changes`. It is the owner's to change while the app runs, so no source file lists a tag or an alias, tests apart; migration 7 wrote the set it starts as, once, and is not a second copy to keep in step. It is read with `getVocabulary` and `listTags`, and changed only by the functions of `packages/core/src/vocabulary.ts`: `addTag`, `acceptTagProposal`, `addTagAlias`, `removeTagAlias`, `dismissTagProposal`, `retireTag`, `renameTag`, `mergeTags`. The classifier's instructions and the tags its answer may hold are built from the vocabulary as it stands when a run begins. *Why: the owner was promised that accepting a proposed tag is a click, not an edit to a source file. A list in the code beside the one in the database would be two vocabularies, and they would disagree the first time the owner used the interface.*
- **LAB-3** Three versions are stored with every classification, and each moves for its own reason. Any change to `TAXONOMY` raises `TAXONOMY.version`. Any change to what the classifier is told or asked with (the wording in `packages/tagger/src/instructions.ts`, the fields of `input.ts`, the model, its settings) raises `INSTRUCTIONS_VERSION`. `taxonomy.test.ts` and `instructions.test.ts` hold the fingerprint of each version and fail when a change was made without it. Any change to the vocabulary that alters what the classifier is told gets the next vocabulary version by itself, in `vocabulary_changes`. A classification made under an older taxonomy or older instructions is outdated, and `pnpm tag --retag` does it again when the owner asks. One made under an older vocabulary is not outdated: see LAB-9. *Why: a bookmark classified before a change was classified under other instructions. The versions are how "which ones" stays a query.*
- **LAB-4** The classifier writes through `recordClassification`, `recordNewTags` and `recordClassificationFailure` and nothing else; the owner's corrections of a bookmark are written by `correctBookmark` and nothing else. The first three never read or write `bookmark_corrections` or `bookmark_tag_corrections`. *Why: the owner's word must outlive every later run, a re-tagging included. Two hands with tables of their own cannot overwrite each other; `labels.test.ts` compares the owner's rows before and after a run.*
- **LAB-5** What a bookmark is filed under is read, never copied: the category and format are `CATEGORY` and `FORMAT` of `bookmarks.ts`, the owner's correction before the classifier's answer, and the tags are the view `bookmark_effective_tags`, which holds only tags the vocabulary has not retired. Filters, counts and `Bookmark.labels` all read those three. *Why: a second place that works out "the tags of a bookmark" will disagree with the first the day a correction or a retired tag is involved.*
- **LAB-6** A tag outside the vocabulary is never on a bookmark. What the classifier suggests is stored as a proposal with the bookmark it was suggested for, and becomes a tag only by the owner's decision, made through `vocabulary.ts`: accepted as a new tag or as another name for one, or dismissed, after which the same text is dropped whenever it is suggested again. Accepting puts the tag on the bookmarks that prompted it, without asking the model again. *Why: free tags drift into three spellings of one subject, and a filter that misses two of them is worse than no filter.*
- **LAB-7** A change to the vocabulary carries the bookmarks with it in the same transaction, and never loses the owner's word. A renamed tag is on the same bookmarks under its new name, corrections included, and its old name becomes an alias. A tag merged into another gives its bookmarks and its corrections to that one. A retired tag keeps its rows and is on no bookmark; restoring it brings them back. `vocabulary.test.ts` holds each. *Why: the owner changes the vocabulary to tidy the library, not to lose what was filed.*
- **LAB-8** Proposals are shown to the owner through `listTagProposals`, which groups names that look like one subject, says which tags of the vocabulary a group resembles, counts the bookmarks, and takes a threshold. The grouping compares names and changes nothing; no code merges, accepts or dismisses a proposal on the strength of it. *Why: a library yields hundreds of proposals made once. The list has to be short enough to read, and a guess about likeness must stay a guess until the owner agrees.*
- **LAB-9** A bookmark classified before a tag joined the vocabulary was never asked about that tag. It is not outdated and is not classified again. Those whose text mentions the tag are candidates for a `new-tags` run, which asks the classifier the usual question and stores, through `recordNewTags`, only tags the bookmark had never been offered: its category, its format, its other tags and its proposals stay as they were. Retiring, renaming and merging need no run at all. *Why: the owner has learnt where things are filed. Adding a tag must be able to add that tag to more bookmarks and must not be able to move any of them.*
- **LAB-10** The two reasons a bookmark is under "other" are kept apart wherever "other" is counted. The classifier says which it is, the answer is stored (`too_little_text`), and `TOO_LITTLE_TEXT` in `bookmarks.ts` is the one expression that reads it: the `tooLittleText` filter, `MatchSummary.tooLittleText`, `LibrarySummary.other` and `summariseTagging` all use it. *Why: they mean opposite things. Too little stored text says nothing about the taxonomy; text enough and no category that fits is the sign that a category is missing, and a single count of "other" hides it.*
- **LAB-11** `recordClassification` checks everything it is given, the category and format against `TAXONOMY` and the tags against the vocabulary as it stands, and throws for what is not in them. The schema does not: categories, formats and tags are stored by id with no `CHECK` on a list. *Why: the lists change with a version or with the owner's click, not with a migration (MIG-2); so the check has to be in the one function that writes.*

## Sending bookmarks to Claude

Tagging is the first thing in this project that sends the owner's data to a third party, and the first that calls any host but the local app. The written part of the weekly digest is the second. It was put in the same package, behind the same client, so that AI-1 to AI-10 hold for it as they stand; AI-11 to AI-13 are what is its own. `packages/tagger/src/boundary.test.ts` reads the repo's source for AI-1, AI-2, AI-5, AI-11 and AI-13, `input.test.ts` and `digest/input.test.ts` pin AI-3 and AI-11, and the X check of X-4 covers AI-4.

- **AI-1** One package calls Claude, `packages/tagger`, and in it one file, `src/anthropic.ts`. Anthropic's SDK is a dependency of that package alone and is imported by that file alone; no other file in the repo names the platform's `fetch` to reach it, and no other package but `packages/web` depends on the tagger, whose one importer there is `src/server/tagging.ts`. The MCP server stays as MCP-2 has it: it loads neither. The package holds two senders, the classifier and, under `src/digest/`, the writer of the weekly digest; both send through that one file, and a third thing that needs Claude goes there too, not into a package of its own. *Why: "what leaves this computer" has to be a question with one file for an answer. A second package with a client of its own would be a second answer, and the checks on the first would not see it.*
- **AI-2** One host: `https://api.anthropic.com`. The client is given that address outright, so the environment cannot move it, and every request passes `onlyToClaude`, which refuses any other origin, passes the address through `assertNotXOwnedUrl` (X-3), switches redirects off, and drops every header but the key, the API version, the content type and the SDK's description of itself. An address the API hands back, such as a batch's results, goes through the same gate. *Why: a base address read from a variable, a redirect, or a results link are three ways the library's text could go somewhere nobody chose.*
- **AI-3** What is sent of a bookmark is `ClassifierInput` in `packages/tagger/src/input.ts` and nothing else: the post's text; X's language code for it; whether it is a reply; for each attached picture or video its kind and the description its author gave it; the link card's title, description and site; the X Article's title and opening; and the same parts of the quoted post. Not sent: the post's id or address, the author's id, handle, name or avatar, any time, any count, the handle replied to, and every stored URL field. The text goes as written, so a handle or link typed into it is part of it. A request holds the instructions, that one object as JSON, and the output schema; no tools, no metadata, no post id: a batch numbers its requests. A new field is its own explained change, here first. *Why: the owner was told what leaves. `input.test.ts` builds a bookmark with a telltale value in every stored field and looks for each in the message.*
- **AI-4** Nothing is fetched to enrich what is sent. The classifier is given what a capture holds and told what is absent: the rest of a thread, the post a reply answers, the media, the page behind a link. It names no host of X's (`no-requests-to-x.test.ts`), makes no request but to the Claude API, and sends no media, which it would have to download first. *Why: X-1 and X-2. Every way of filling a gap is a request to X.*
- **AI-5** The API key is one line of the git-ignored `.env` at the repo's root, under `X_BOOKMARKS_ANTHROPIC_API_KEY`, a name of this project's own; `.env.example` is committed and gives it no value. `readApiKey` in `packages/tagger/src/api-key.ts` is the one function that reads it, from the file: it is not taken from any environment, under either name, and the client is handed it as an argument, with `authToken: null` and logging off. It is never written to `process.env`, and appears in no message, log, report or stored row. Nothing in the repo loads a `.env` file into an environment (no `dotenv`, no `--env-file`), and `packages/web` holds no `.env*` file of its own, which is the only place Next loads one from; so the key is in no process's environment, the app's included. A key under `ANTHROPIC_API_KEY`, in the environment or in the file, is never used, and `standardKeyWarning` says so wherever the classifier starts. `readApiKey` refuses, saying what to do, when the file is missing, gives the variable no value, is not shaped like a key, or can be read or written by another user; that last is a refusal and not a warning because the app's own passes have no terminal to warn in. A moved data directory (`X_BOOKMARKS_DATA_DIR`) has its key file inside it, so a test or a tool on another library never finds the owner's key. *Why: `ANTHROPIC_API_KEY` outranks a Claude Code subscription login. Under that name, in the environment of Claude Code, `claude -p` or an Agent SDK process, a key silently bills the owner's other work to the API. A name nothing else reads cannot do that, wherever the file ends up loaded.*
- **AI-6** A post is material and never instruction. The instructions are the system prompt, which holds nothing of any post; the post is one JSON object in the user message; there are no tools; and the answer is held by the API to a schema whose category and format are enums of the taxonomy and whose tags are an enum of the vocabulary. `readAnswer` checks the answer again. The one free text in it, a proposed tag, is kept only when it is shaped like a tag, is capped at two a post, and is never applied (LAB-6). The names of proposals already made are the one thing a run is told that began as a model's output; they are tag-shaped, they are given as names to reuse, and the schema does not admit them as tags. Hidden characters are dropped by `visibleText` before sending. *Why: posts are written by strangers. A model can be talked into things; what it is talked into can then only be a wrong label from the list, which the owner can correct.*
- **AI-7** A run has a spend cap it cannot exceed, kept with `mostOf` in `pricing.ts`: the most a request can cost whatever the model does. Prices are written in that file alone. The app's own passes do two things: they classify bookmarks with no answer, and they ask about bookmarks that mention a tag added since they were classified, which can only add that tag (LAB-9). They leave a backlog of more than `BACKLOG_LIMIT` of either to the owner, and spend at most `PASS_CAP_USD` a pass and `DAILY_CAP_USD` a day; a bookmark the model fails on twice is not asked about again by itself. The first run, a backfill and a re-tagging are started by the owner (`pnpm tag`). *Why: an unattended loop against a paid API has to be unable to cost more than cents, and unable to move what the owner has filed.*
- **AI-8** Tagging never holds up or loses a capture. The ingest route asks for a pass and answers the extension without waiting; a pass never throws; a missing key, an unreachable API or a broken pass leaves the bookmarks stored, parsed and unclassified for the next pass. *Why: PARSE-7, one step further. The API is another party's and is sometimes away.*
- **AI-9** What a run prints, logs or stores about itself is counts, ids of the taxonomy, token counts and money: `packages/tagger/src/report.ts` and `src/digest/report.ts`, and the `tagging_runs`, `classification_failures` and `digest_runs` tables. No post text, author, address or model output. The one exception is the thing a digest run exists to make: the digest's text, in `digest_runs.body`, stored on the terms of AI-12 and never printed or logged. *Why: PRIV-5. A report is pasted into terminals and transcripts, and the schedule's log is a file.*
- **AI-10** No test calls the API or reads the repo's own `.env`, and no test or agent runs `pnpm tag` or `pnpm digest` without `--dry-run`. The classifier is tested through its real client over `packages/tagger/src/testing/fake-api.ts`, a fake at the HTTP boundary that rejects what the API would reject. `createClaude` refuses to build a client for the real API in a process a test runner started, the end-to-end test's app included. *Why: TEST-4, and a test that spends the owner's money is not a test.*

- **AI-11** Of a bookmark, the digest sends what the classifier sends and no more. `packages/tagger/src/digest/input.ts` gets each post from `classifierInput(bookmark, DIGEST_TEXT_LIMITS)`, the one function of AI-3, which refuses a limit above the classifier's; it reads no field of a bookmark itself, and adds one thing, the post's number in the message. The request is the instructions, that message and the answer's schema: no post id, no author, no time, not the week's dates, not how a bookmark is filed, no tools, no metadata. Bookmarks removed on X are not sent. A change to the wording, the answer's shape, the limits or the model raises `DIGEST_INSTRUCTIONS_VERSION`, and `digest/request.test.ts` holds each version's fingerprint. *Why: the owner was told what leaves, once, in one table. A second list of fields would be a second promise to keep, and the digest sends a whole week at a time.*
- **AI-12** A digest is a model's words about strangers' posts, and is treated as such from the answer to the screen. The answer's schema admits a post only as a number of that request; `readDigest` turns a number into a post id through the run's own list and drops any other; core's `finishDigestRun` refuses an id the run did not send, and stores each string without hidden characters, control characters or anything written as an address, within `DIGEST_LIMITS`. A screen shows the prose as text, never as markup, makes no link out of it, and draws each bookmark it names with the library's own components; the MCP server returns it under MCP-3. *Why: AI-6, one step further. A classification can only be a wrong label from a list; a digest is free text, so what it can do is bounded at each place it is read instead: it can be wrong, and it cannot be a link, an instruction with authority, or a pointer at anything but a bookmark of its week.*
- **AI-13** A digest is written when the owner asks, and never otherwise. The one thing that starts a run is `pnpm digest`: at a terminal, or from the launchd job of `packages/tagger/launchd/`, which the owner installs by hand and no code or agent installs, loads or starts. Nothing in `packages/web` or `packages/mcp` imports the digest's modules, calls `writeDigest` or opens a run with `startDigestRun`; the app shows a stored digest, or the command that writes one. A run cannot exceed its cap, kept with `mostOf` (AI-7) at the digest's own output limit, with each attempt that brought no answer held against it; it writes no week a second time unless told `--again`; and it is recorded in `digest_runs` with the model, the instructions version, the tokens and the cost. *Why: it costs money each time, and unlike a tagging pass it is not needed for the library to work. The owner was told that nothing in the app would generate it by itself.*

What these checks cannot see: what Anthropic does with what it is sent, which its terms govern and no test here can; a request made inside the SDK that is not the one asked for; and whether the fake matches the API, which only the first real run shows.

## Capture extension

- **CAP-1** The extension sends no request to any X host and alters none: no `fetch`, XHR, navigation, `webRequest` or `declarativeNetRequest` rule aimed at X, and no scrolling, clicking or other scripting of the page. The wrappers in `src/hook.ts` call the browser's own function with the page's own `this` and arguments. *Why: accounts have been suspended for extensions that made their own requests to X; nothing is reported for reading what the page loaded. This is the user's account.*
- **CAP-2** The captured operations are named in `CAPTURED_OPERATIONS` in `packages/extension/src/operations.ts` and nowhere else. For any other request the page hook reads the URL and nothing more, and reports nothing. Adding an operation is its own explained change. *Why: the user was promised that only bookmark responses leave the page.*
- **CAP-3** In `manifest.json`, `host_permissions` is the app's origin alone, the content scripts match `https://x.com/*` alone, and there is no `externally_connectable` or `web_accessible_resources`. A new permission is its own explained change. *Why: without a host permission for X the service worker cannot read X at all, and the page cannot reach the extension. `protocol.test.ts` pins this.*
- **CAP-4** The extension forwards response text and does not parse it. *Why: a parser fix must never require reinstalling the extension, and the stored text must be what X sent.*
- **CAP-5** Only the service worker talks to the app, at `APP_ORIGIN`. *Why: a content script's request is made as x.com. Chrome's Local Network Access check gates that behind a permission prompt, and the app would have to accept x.com as an origin. The service worker's request carries the extension's own origin and, with the host permission, is exempt from the check.*
- **CAP-6** A capture leaves the extension's queue only on an answer that carries the app's proof and names that capture as stored or duplicate. No capture is sent before the app has proved itself in that delivery pass. *Why: the app is often closed while the user browses, and then anything may be listening on its port. A bare 200 from it must neither receive bookmarks nor delete them.*
- **CAP-7** A change to `src/hook.ts` or `src/page-hook.ts` keeps the shapes test in `packages/e2e` passing: with and without the extension, X receives the same requests with the same headers in the same order and the same bodies, and the page observes the same results. A difference from the browser's own functions that the page can observe is either removed or added to the list in the extension's README, and to the `known` block the test pins. *Why: a behavioural difference in X's page is both a bug risk and a way to be noticed.*
- **CAP-8** Nothing is added whose only purpose is to hide the extension from the page: no rewriting of stack traces, no faking of `toString`. *Why: the user was told there is no cloaking. Being a faithful wrapper is the goal; being invisible is not.*
- **CAP-9** A capture's time is set by the service worker's clock when the capture reaches it. No value from the page, the hook or the relay carries a time. *Why: any script in an x.com page can fire the hook's event, and this time becomes a bookmark's first-seen.*
- **CAP-10** The retry alarm exists whenever captures are waiting, from the moment one is queued. *Why: Chrome stops the service worker at will, mid-delivery included, and only an alarm starts it again.*

## Ingest endpoint

- **ING-1** A route that accepts data calls `refuseUnlessExtension` first. It reads headers only, so a refused request's body is never read. *Why: any page the user visits can post to a localhost port. The `Origin` check keeps out every web page, the signature keeps out whatever can forge headers but does not hold the token, and the `Host` check keeps out a domain re-pointed at 127.0.0.1.*
- **ING-2** No response carries an `Access-Control-Allow-*` header, and `OPTIONS` is refused. *Why: the extension needs neither, so every preflight is from a page that should fail.*
- **ING-3** The app's start scripts bind `127.0.0.1` and the port in `APP_PORT`. *Why: the default is every interface, which exposes the library to the local network. `ingest.test.ts` pins this.*
- **ING-4** The pairing token is never sent, served or logged. It exists in `data/ingest-token`, in the extension's storage, and in the terminal output of `pnpm pair`. Requests are signed with it and answers are proved with it (`packages/extension/src/auth.ts`); no page or route returns it. *Why: a token that crosses the wire is learnt by whatever is listening, and a token on a page is learnt by anything that can load the page. `ingest.test.ts` pins which files read it.*
- **ING-5** Every answer to an authenticated request is made with `provenAnswer`; a refusal by `refuseUnlessExtension` carries no proof. *Why: the proof is how the extension tells the app from an impostor, and an unauthenticated caller must not be handed anything signed with the token.*
- **ING-6** The API routes stay outside `src/proxy.ts`'s matcher. *Why: Next buffers the body of a request that passes through the proxy and silently cuts it at 10 MB.*

## First-seen

- **SEEN-1** No function parameter or input type, in core or outside it, carries a first-seen time. It is copied from the capture's `received_at` inside `upsertBookmark`. *Why: X exposes no bookmark time, so the weekly digest rests on this value. A caller-supplied time would be the parser's run time, which is wrong on every re-parse.*
- **SEEN-2** Rows in `bookmarks` are written by `upsertBookmark` only. No `INSERT OR REPLACE`, `REPLACE INTO`, or delete-then-insert touches the table. *Why: REPLACE deletes and re-inserts the row, which resets first-seen without firing the update trigger.*
- **SEEN-3** The `bookmarks_first_seen_is_immutable` trigger stays. A migration that rebuilds `bookmarks` copies `first_seen_at` and `first_seen_capture_id` unchanged and recreates the trigger. *Why: it is the last guard if SEEN-2 is missed.*
- **SEEN-4** "Added in this period" is computed from `first_seen_at`, never `posted_at` or `last_seen_at`. *Why: an old post bookmarked today has an old `posted_at`, and `last_seen_at` moves on every sync.* Since the parser phase there is also `estimated_bookmarked_at`, and after a backfill `first_seen_at` is the same day for the whole library. Since the read phase the decision is made, in READ-2: features that ask "bookmarked in this period" use `bookmarkedAt`, which falls back to `first_seen_at` only where there is nothing better. `first_seen_at` remains the answer to "entered the library in this period".
- **SEEN-5** `estimated_bookmarked_at` is derived inside `upsertBookmark` from the sighting's `sortIndex`, by `estimateBookmarkedAt`, and is null unless it falls between the post's time and the capture's. It is never copied into `first_seen_at`, and no input carries it. *Why: it decodes a value X does not document. It held on all 1,446 real bookmarks of the first capture, and the day X changes the value's meaning it must turn into nulls and a recorded warning, not into wrong dates.*

## Schema and migrations

- **MIG-1** A schema change is a new file `packages/core/src/migrations/NNNN-name.ts`, numbered one above the last and added to the end of the list in `migrations/index.ts`. No `CREATE`, `ALTER` or `DROP` runs from anywhere else. *Why: `openStore` is the single place a database is brought up to date.*
- **MIG-2** A migration that already exists on the main branch is not edited, renamed or removed. *Why: its checksum is recorded in every database it ran on, and `openStore` refuses a database whose applied migrations differ from the code.*
- **MIG-3** Migration SQL contains no `BEGIN`, `COMMIT` or `ROLLBACK`. *Why: each migration runs inside one transaction so that a failure leaves the database untouched.*
- **MIG-4** New tables are `STRICT`. *Why: without it SQLite stores a string in an integer column without complaint.*
- **MIG-5** A timestamp column is an `INTEGER` holding Unix epoch milliseconds, named `*_at`, with `CHECK (col > 1000000000000)`. Core's public types expose it as `Date`. A week is not a timestamp: `digest_runs.week` holds its name, the local date of its Monday, as text (READ-8). *Why: one unit and one type make comparisons in SQL correct, and the check rejects seconds passed by mistake.*
- **MIG-6** X ids (posts, users) are `TEXT` columns holding decimal digits, and `string` in TypeScript. *Why: they exceed 2^53 and lose digits as JavaScript numbers.*

## Privacy

- **PRIV-1** The diff contains no database file, no unredacted captured response, no `.env` file, and no token or cookie value. *Why: the library is one person's private reading history, and X session cookies grant full account access.*
- **PRIV-2** A fixture is cut down to the entries its test needs and has the account owner's ids and handle removed. *Why: fixtures are committed.*
- **PRIV-4** A fixture made from a real capture is written by `pnpm fixtures:build` and by nothing else, and `pnpm fixtures:check` passes on the machine that holds the captures before it is committed.
